# 0001：行为事件日志作为唯一事实来源

- 状态：Accepted
- 日期：2026-08-18
- 决策者：项目负责人

## 背景

本项目（笼养动物健康管理）的产品核心是「把一天十几个小时的笼内视频与声音，压缩成几分钟能读懂的行为日报，并在宠物偏离个人基线时提醒主人」（见 `docs/project-background.md`）。这条链路会产生多种下游产物：日报、个体基线、异常提醒、兽医报告、审计记录。

如果每个下游产物各自维护自己的状态（例如日报表、基线表、提醒表互相独立、各写各的），会出现三类问题：

1. **不可追溯**：一条异常提醒无法回答「它由哪条原始行为事件、哪版规则、哪版模型产生」，无法满足 `docs/architecture.md` 的「可追溯」要求。
2. **不可重放**：修改行为规则或模型后，历史报告与基线无法按新逻辑重新生成，无法「用今天的认知重新理解昨天的数据」。
3. **不一致**：同一事实在多个地方被复制，改一处漏一处，最终日报、基线与提醒彼此矛盾。

DeepSeek Harness（`dsh`）在 `docs/architecture.md` 中有一条同构的不变量：**Model-visible ⟺ logged**——凡是进入模型请求的内容，都必须能从会话日志重建；fork、resume、telemetry、持久化全部从这一条事件流派生。本决策把这一思想迁移到本项目的「行为事件」领域。

## 决策

**采用 append-only（只追加）的「行为事件日志」作为整个系统的唯一事实来源。**

具体含义：

1. **只追加、不改写、不删除**：事件按 `seq` 单调递增顺序写入；修正错误用「补偿事件」表达，而非修改或删除历史事件。
2. **下游产物都是「投影（projection）」，不是独立事实**：日报、个体基线、异常提醒、兽医报告均从事件流聚合/投影得出，可随时由事件流重建。
3. **每条事件自带溯源字段**：至少包含 `ruleVersion` 与 `modelVersion`，异常可追溯到「哪条事件 + 哪版规则 + 哪版模型」。
4. **模型可见 ⟺ 已落日志**：凡是进入「大模型解释层」或进入「面向用户的结论」的输入，都必须能由事件日志重建；新增一种模型/用户可见输入，就必须先新增一种事件类型。
5. **存储后端可替换**：MVP 用 JSONL（每笼每日一个文件，天然可重放、可 `grep`），后续可换 SQLite；后端通过 `storage` 接缝切换，事件信封与投影逻辑不变。

事件信封与事件类型的草案见 `docs/architecture-proposal.md` 第 5 节（信封字段：`seq` / `ts` / `kind` / `birdId` / `cageId` / `sessionId` / `ruleVersion` / `modelVersion` / `payload` / `videoRef` / `source`）。

## 备选方案

### 方案 A：各模块各自建表/存状态（未采用）

日报、基线、提醒各维护自己的存储，事件只作为中间产物不持久化。

- 优点：实现最直接、初期开发最快。
- 缺点：不可追溯、不可重放、易不一致；换规则/模型后历史数据无法复用，与「个体基线」「可追溯」这两个产品壁垒直接冲突。

### 方案 B：以「原始视频 + 时间戳索引」为唯一事实来源（未采用）

不落结构化事件，只存视频与时间轴索引，需要时再临时识别。

- 优点：保留最多原始信息，理论上最「无损」。
- 缺点：每次出日报/基线都要重跑全量识别，成本与延迟不可控；结构化事件才是用户真正关心的产品对象（见 `project-background.md`「事件才是产品核心」）；索引粒度也仍需结构化事件来锚定。

### 方案 C：事件日志 + 关系型数据库双写（未采用）

事件落日志，同时同步写入业务表。

- 优点：查询性能好。
- 缺点：引入「日志」与「业务表」双事实来源，需要保证两者一致（双写一致性问题）；违背「唯一事实来源」的核心目标，维护成本高。

## 影响

**正面：**

- 满足「可追溯、可复核、可验证」非功能要求：任何提醒都能追到原始事件与版本。
- 支持重放：改规则/模型后可重新投影历史日报与基线，支撑「个体基线」长期演进。
- 降低不一致风险：下游只有一个事实来源，投影逻辑集中。
- 便于测试：事件流是确定性的、可回放的输入，适合做快照/回放测试（对应 dsh 的 keyless snapshot 思路）。

**代价与风险：**

- 需要先投入设计事件 schema（信封与事件类型），并在 MVP 早期就遵守「只追加」纪律，初期略有额外成本。
- JSONL 在全量重放大历史时的性能需在后续评估；必要时用 `storage` 接缝切换 SQLite 或引入投影缓存。
- 「补偿事件」的语义需要单独约定，避免把补偿做成一堆难以理解的补丁。

**后续工作：**

- 定稿事件信封与 MVP 事件类型（`capture.frame_dropped`、`detect.*`、`behavior.food_visit`、`behavior.activity`、`behavior.long_stillness`、`behavior.social_interaction`、`behavior.vocalization`、`baseline.snapshot`、`report.generated`、`alert.raised`、`review.approved` 等）。
- 约定 `birdId` / `cageId` / `sessionId` 取值规则、时区与保留期。
- 定义 `storage` 接缝（本地 JSONL 为首个 Provider）。

## 验证

- 用最小链路证明可行性：`capture → detect → 一条 behavior 事件 → 写入日志 → 从日志投影出一句日报文案`，跑通「食盆访问」全流程。
- 可重放性验证：对同一段事件流，用两版不同规则/模型重新投影，日报输出应随版本变化、且事件流本身不变。
- 可追溯性验证：构造一条 `alert.raised`，断言能沿 `triggerEventKind` 与版本号回溯到原始 `behavior.*` 事件。
- 一致性验证：删除/清空所有投影产物后，仅凭事件流能重建日报与基线。
