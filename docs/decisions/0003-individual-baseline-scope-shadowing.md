# 0003：个体基线采用「scope + shadowing」模型

- 状态：Accepted
- 日期：2026-08-18
- 决策者：项目负责人

## 背景

产品壁垒之一是**个体基线**：记录 7–14 天后，为每只鸟建立「自己的正常」，异常是和**这只鸟自己**比，而不是和「标准鹦鹉」比（见 `docs/project-background.md`）。

这带来三个现实问题：

1. **冷启动**：新用户没有 7–14 天历史数据时，系统必须给出某种基线，否则无法产日报与提醒。
2. **多鸟与身份缺失**：多鸟外观相似、个体追踪难；首版可能退化为「只分析笼体整体，不区分个体」（`birdId=cage`）。此时「个体基线」无从谈起，需要「笼级基线」兜底。
3. **边界要清晰**：当个体基线与全局基线都存在时，以哪个为准、如何切换、如何标注来源，必须显式约定，不能靠隐式 `if` 散落在代码里。

DeepSeek Harness（`dsh`）用 **scope + shadowing** 表达同类问题：全局注册对所有人可见；作用域（scope）注册只对某个主体生效，并且「最具体者胜」（shadowing）——per-agent 的 persona/工具变体覆盖同名的全局默认。本决策把这一思想迁移到「基线」领域。

## 决策

**个体基线采用「scope + shadowing」模型：per-bird 基线覆盖全局默认基线，无个体基线时显式回退全局，并始终标注实际使用的基线来源。**

### 基线层级（三级，从具体到兜底）

| 层级 | 键（scope key） | 来源 | 用途 |
|---|---|---|---|
| 个体基线 | `bird:<birdId>`（如 `bird:lumi`） | 该鸟 7–14 天的历史事件聚合 | 首选，和「这只鸟自己」比 |
| 笼级基线 | `cage:<cageId>` | 笼内整体事件聚合（身份缺失时） | 身份未识别时的兜底 |
| 全局默认基线 | `species:<species>`（如 `species:lovebird`） | 物种通用统计（冷启动） | 新用户冷启动兜底 |

### 三条规则

1. **最具体者胜（shadowing）**：查询某只鸟的基线时，按 `bird → cage → species` 顺序取**第一个存在**的层级；更具体层级的对应指标覆盖更笼统层级，其余指标继承（而非整体替换）。
2. **显式标注来源，不伪装**：每次基线对比的结果必须携带实际使用的基线键（`baselineSource`），例如「本日指标与 `bird:lumi` 对比」或「冷启动，与 `species:lovebird` 对比」。不得把回退结果表述成个体结论。
3. **基线是可重放投影，不存独立状态**：基线从事件流聚合得到（对应 ADR-0001），可随事件增长/重放重建；`baseline.snapshot` 事件只是「某时点投影快照」，供日报引用，不是第二事实来源。

### 数据与事件

- 每日聚合指标建议包含：活动时间分布、食盆访问次数、夜间静止时长、鸣叫频率、社交时长、长时间静止次数（草案，见 `docs/architecture-proposal.md` 第 5.3 节 `baseline.snapshot`）。
- 异常判定输出 `Deviation`（如 `food_visits_change: -35%`），并携带 `baselineSource` 与统计口径（窗口长度、观测天数）。

## 备选方案

### 方案 A：只做全局物种基线（未采用）

所有鸟共用一份「标准鹦鹉」基线。

- 优点：实现最简、无身份依赖、冷启动天然可用。
- 缺点：丢掉了「和这只鸟自己比」这一产品壁垒，无法捕捉个体差异，与愿景核心冲突。

### 方案 B：只做个体基线、不做兜底（未采用）

没有 7–14 天数据就不产基线。

- 优点：逻辑最纯粹。
- 缺点：冷启动期无产品价值，新用户体验差；身份缺失时直接不可用，与「首版可退化为整体笼态」冲突。

### 方案 C：为每个物种硬编码阈值（未采用）

写死「牡丹鹦鹉每天进食 N 次」等阈值。

- 优点：无需统计与冷启动。
- 缺点：无法个体化、无法随数据演进；阈值维护成本高且难验证，与「可追溯」「个体基线」目标不符。

## 影响

**正面：**

- 冷启动、身份缺失、个体成熟三种状态都被同一套层级模型覆盖，逻辑集中。
- 「和这只鸟自己比」落地为显式的 `bird:` 键与 shadowing 语义，成为可测试、可追溯的机制。
- 与 ADR-0001（事件日志唯一事实来源）正交：基线是投影，可重放、可重建。

**代价与风险：**

- 需要约定「对应指标覆盖、其余继承」的 shadowing 粒度，否则会出现部分指标来自个体、部分来自物种的混淆。
- 多鸟身份解析错误时，个体基线可能「张冠李戴」，需在 `detect` 接缝与数据标注上控制（见 ADR-0002 的 `birdId` 语义）。
- 基线窗口、观测天数、保留期需另行确认，避免基线漂移或过拟合。

**后续工作：**

- 定稿每日聚合指标 schema 与 `Deviation` 结构。
- 约定 shadowing 的粒度（逐指标 vs 整体）与 `baselineSource` 取值规则。
- 建立 `baseline.snapshot` 事件的写入与保留策略。

## 验证

- 冷启动：对一个没有历史数据的新 `birdId` 查询基线，断言回退到 `species:lovebird` 且 `baselineSource` 正确标注。
- shadowing：为 `bird:lumi` 写入个体基线后，断言查询命中 `bird:lumi` 而非全局；且未覆盖指标继承自更笼统层级。
- 身份缺失：`birdId=cage` 时，断言走 `cage:` 层级而非 `species:`。
- 可重放：仅凭事件流重新投影出与已有 `baseline.snapshot` 一致的基线（对应 ADR-0001 的验证）。
